# Plan d'implémentation — premier accès BA26

## Décision fonctionnelle proposée

Le premier accès utilisera exclusivement le lien Supabase de récupération existant, valable une heure et remplacé à chaque relance. Aucun mot de passe temporaire ne sera généré, affiché, exporté ou stocké. HEDS25-508 reste responsable de la création des comptes ; ce ticket gère uniquement l'envoi, le suivi et la consommation du premier accès.

## Tâches

- [ ] **1. Ajouter le stockage serveur du suivi et de l'historique.**
  - Objectif : créer `public.student_initial_access` avec une ligne unique par `user_id`, les états `pending|sent|used|expired|error`, les dates, le compteur de tentatives et un code d'erreur générique ; créer `public.student_initial_access_events` pour l'historique append-only.
  - Fichiers attendus : une nouvelle migration dans `supabase/migrations/`, `supabase/baseline/public-schema.sql` généré par les outils du dépôt, catalogue de schéma associé si requis par le garde-fou.
  - Autorisé : clés étrangères vers `user_profiles`, contraintes CHECK, index ciblés, RLS, grants service role.
  - Interdit : écrire dans `auth.*`, stocker email, mot de passe, OTP, URL ou jeton ; policy `anon`/`authenticated` ; modification destructive d'une table existante.
  - Tests : garde-fou du schéma, assertions SQL/RLS et test d'absence de colonnes sensibles.
  - Validation : `npm run db:schema:check` puis vérification des advisors sur l'environnement de test avant toute application en production.
  - Sécurité/rollback : migration append-only ; rollback applicatif en cessant d'appeler les nouvelles routes, sans supprimer les traces.

- [ ] **2. Extraire un service backend de premier accès testable.**
  - Objectif : valider UUID, profil étudiant actif, classe strictement BA26/BAC26, compte Auth et adresse Auth ; produire l'état courant sans exposer de donnée sensible.
  - Fichiers attendus : `backend/supabase/studentInitialAccessService.js`, tests dans `backend/test/studentInitialAccess.test.js`.
  - Autorisé : réutiliser `isStudentProfile`, injecter client DB/Auth, horloge et générateur d'identifiants pour les tests.
  - Interdit : faire confiance au rôle, à la classe ou à l'adresse envoyés par le navigateur ; utiliser `user_metadata` pour l'autorisation ; journaliser les erreurs Auth brutes.
  - Tests : étudiant BA26/BAC26, rôle interdit, autre cohorte, inactif, compte absent, adresse Auth absente, timeout et erreur fournisseur.
  - Validation : `npm --prefix backend test`.
  - Sécurité/rollback : échec fermé avant tout envoi ; aucune mutation de compte Auth.

- [ ] **3. Ajouter les routes administrateur d'état, d'envoi et de relance.**
  - Objectif : exposer la liste des états et un endpoint idempotent d'envoi/relance sous `/api/admin/users`, protégés par le middleware existant `authenticate + requireAdmin`.
  - Fichiers attendus : `backend/supabase/adminUsersBackend.js`, `backend/supabase/passwordRecoveryRequestBackend.js` seulement si une fonction d'envoi sûre doit être partagée, tests backend dédiés et `backend/test/security.test.js`.
  - Autorisé : destination de récupération calculée côté serveur, `resetPasswordForEmail`, catégories d'événements génériques, expiration calculée à 3 600 secondes.
  - Interdit : accepter une adresse ou une URL de redirection du client ; retourner l'existence d'un compte à une route publique ; créer un nouveau compte lors d'une relance.
  - Tests : autorisation, destination imposée, un seul enregistrement courant, relance, erreur d'envoi, réponse/logs sans secret.
  - Validation : `npm run test:security`.
  - Sécurité/rollback : la route est additive et peut être désactivée sans casser le parcours public de mot de passe oublié.

- [ ] **4. Marquer l'accès utilisé après un changement de mot de passe réussi.**
  - Objectif : ajouter un endpoint authentifié idempotent qui ne peut marquer que la ligne de `req.auth.userId`, puis l'appeler avant la révocation de la session de récupération.
  - Fichiers attendus : route backend dédiée montée après `authenticate`, `src/service/passwordRecoveryService.js`, tests unitaires du service et tests backend.
  - Autorisé : no-op si aucun premier accès n'existe, transition `sent|expired -> used`, horodatage serveur.
  - Interdit : recevoir un autre `user_id`, un email, un jeton ou un mot de passe ; accepter une transition vers un autre état depuis le navigateur.
  - Tests : succès, appel répété, mauvais utilisateur impossible, absence d'enregistrement, échec réseau ne révélant aucun secret.
  - Validation : `npm run test:unit -- --run tests/unit/passwordRecoveryService.spec.js tests/unit/resetPasswordJourney.spec.js` et `npm --prefix backend test`.
  - Sécurité/rollback : si le suivi échoue après le changement de mot de passe, la connexion reste valide et l'état admin devient réconciliable/relançable sans bloquer l'étudiant.

- [ ] **5. Remplacer le mot de passe administrateur par l'action d'accès initial.**
  - Objectif : dans `UserListView.vue`, supprimer la saisie/génération/transmission du mot de passe, afficher l'état de premier accès et proposer « Envoyer l'accès » ou « Renvoyer » avec confirmation et retour clair.
  - Fichiers attendus : `src/views/admin/users/UserListView.vue`, un service frontend dédié si nécessaire, tests de composant ciblés.
  - Autorisé : badges d'état, dates non sensibles, filtres, action par identifiant UUID.
  - Interdit : afficher/copier/exporter un mot de passe, OTP, jeton ou URL ; réutiliser l'ancien formulaire Firebase `NewUserForm.vue` ; exposer la clé service role.
  - Tests : états, action désactivée pour non-BA26/non-éligible, relance, erreur générique, navigation clavier et rendu mobile.
  - Validation : `npm run test:unit` puis `npm run build`.
  - Sécurité/rollback : l'ancien champ de mot de passe ne sera pas conservé derrière un flag ; la création de comptes reste déléguée à HEDS25-508.

- [ ] **6. Documenter et vérifier le parcours complet.**
  - Objectif : étendre la recette pour l'import HEDS25-508, l'envoi admin, l'expiration, la relance et l'état utilisé, avec preuves expurgées.
  - Fichiers attendus : `documentation/docs/testing/password-recovery-recette.md` et la documentation Auth/ops concernée.
  - Autorisé : comptes de test, identifiants de corrélation, codes d'état génériques.
  - Interdit : vrais étudiants, adresse visible, capture de lien complet, OTP, JWT ou mot de passe.
  - Tests : scénario E2E simulé automatisé ; recette manuelle sur un compte BA26 de test après disponibilité de HEDS25-508.
  - Validation : `npm run build:all` et contrôles qualité de la PR.
  - Sécurité/rollback : aucun envoi réel avant validation manuelle explicite sur l'environnement cible.

## Correspondance avec les critères d'acceptation

- Accès unique propre au compte : tâches 1 à 3.
- Expiration, réutilisation et mauvais compte refusés : tâches 2 à 4.
- Connexion puis état utilisé : tâche 4 et recette 6.
- Aucun secret en clair : contraintes transversales des tâches 1 à 6.
- Relance sans doublon : tâches 1 et 3.
- Tests succès/expiration/réutilisation/mauvais compte/relance : tâches 2, 3, 4 et 6.

## Condition de démarrage

Le plan doit être passé à `validated: yes` par validation humaine avant toute modification applicative. La recette réelle et tout envoi à une adresse étudiante restent bloqués jusqu'à la livraison de HEDS25-508 et à la disponibilité d'un compte BA26 de test.
