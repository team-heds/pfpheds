# HEDS25-615 — Empêcher les récompenses au mauvais utilisateur

## Objectif

Garantir qu'une action de gamification ne puisse concerner que l'utilisateur de
la session Supabase et qu'une consultation ou modification administrative d'un
profil tiers ne déclenche aucune récompense personnelle.

## État vérifié

- La RPC Supabase utilise déjà exclusivement `auth.uid()` et n'accepte aucun
  identifiant de bénéficiaire.
- Le service frontend acceptait encore un `userId` fourni par l'appelant et
  rafraîchissait le cache correspondant, même si la RPC récompensait la session.
- La sauvegarde interne du profil déclenchait la gamification avant le contrôle
  explicite `profil consulté = utilisateur connecté`.

## Plan d'implémentation

- [x] Vérifier l'identité avec `supabase.auth.getUser()` avant chaque appel de
  récompense.
- [x] Refuser l'action avant la RPC lorsque la cible diffère de la session.
- [x] Invalider et recharger uniquement le cache de l'utilisateur authentifié.
- [x] Supprimer le déclenchement prématuré lors de la sauvegarde d'un profil et
  conserver un seul déclenchement dans le parcours de son propre profil.
- [x] Supprimer le helper local inutilisé permettant encore de choisir une cible
  et un montant depuis la vue profil.
- [x] Ajouter les tests unitaires identité absente, identité différente et
  parcours administrateur.
- [x] Rejouer les tests SQL d'isolation existants et déployer uniquement le
  frontend de test après validation.

## Critères d'acceptation

1. Une cible différente de la session échoue avant tout appel RPC.
2. Une session absente échoue avant tout appel RPC.
3. Une action valide ne transmet ni identifiant utilisateur ni montant XP à la
   RPC.
4. Modifier un profil tiers ne déclenche pas `onProfileUpdate`.
5. Modifier son propre profil déclenche exactement une fois l'intégration.
6. Les tests SQL confirment qu'une action ne peut modifier les XP d'un tiers.

## Retour arrière

Les changements sont limités au garde d'identité frontend et au déclenchement
de la vue profil. Aucun schéma ni historique n'est modifié. Le retour arrière
consiste à restaurer ces fichiers applicatifs ; la production reste inchangée.
