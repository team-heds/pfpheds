# Plan d’implémentation — filtres métier du dashboard admin

## Objectif

Ajouter des filtres fiables, persistants et accessibles au dashboard admin, dont les options et l’application sont contrôlées par le serveur Supabase authentifié, sans changer les métriques existantes ni exposer de données personnelles.

## Étapes

- [x] **Formaliser le contrat de filtres serveur.**
  - Fichiers : nouveau module `backend/dashboard/adminDashboardFilters.js`, `backend/dashboard/adminDashboardContract.js`, `docs/contracts/admin-dashboard-v1.md`.
  - Limites : conserver la version et la compatibilité des appels sans filtre ; définir les clés, valeurs multiples, limites, codes d’erreur, `appliedFilters` et matrice d’applicabilité.
  - Tests : parsing unitaire, ordre canonique, déduplication, limites et combinaisons invalides.
  - Commande : tests backend ciblés du dashboard.
  - Sécurité : liste blanche stricte ; aucun détail SQL dans les erreurs.
  - Retour arrière : retirer les champs optionnels et le module sans impact sur les appels v1 existants.

- [x] **Créer l’endpoint d’options autorisées.**
  - Fichiers : `backend/dashboard/adminDashboardStatsBackend.js`, service backend de filtres, tests backend.
  - Limites : `GET /v1/filter-options`, même JWT et mêmes autorisations de domaine que `/v1/stats`; réponse uniquement composée d’identifiants métier et libellés non personnels.
  - Tests : admin, enseignant autorisé, domaine interdit, option désactivée/inconnue, réponse sans email/nom d’utilisateur.
  - Commande : tests backend ciblés et contrôles de sécurité.
  - Sécurité : ne pas ajouter de route publique ni de lecture navigateur ; filtrer les référentiels selon les domaines du demandeur.
  - Retour arrière : supprimer la route d’options, sans migration de données.

- [x] **Appliquer les filtres dans les agrégats avec une matrice explicite.**
  - Fichiers : `backend/dashboard/adminDashboardStatsService.js`, module de filtres, contrat documentaire et tests.
  - Limites : classe/cohorte/filière/rôle sur les métriques de profils ; PFP/institution/statut sur les métriques PFP ; les métriques non applicables restent globales et sont marquées comme telles.
  - Tests : au moins un cas positif et négatif par famille, période courante/précédente identiquement filtrées, zéro réel distinct d’une erreur.
  - Commande : suite `adminDashboardStats` et tests de régression sécurité.
  - Sécurité : valeurs validées puis passées aux opérateurs Supabase ; aucun SQL construit par concaténation.
  - Retour arrière : rétablir les définitions de requêtes sans prédicat ; aucune donnée persistée.

- [x] **Étendre le client frontend et son cache.**
  - Fichiers : `src/service/adminDashboardStatsService.js`, `src/composables/useAdminDashboardStats.js`, tests unitaires frontend.
  - Limites : sérialisation multivalue stable, validation de `appliedFilters`, endpoint d’options, clé de cache incluant tous les filtres et déduplication conservée.
  - Tests : deux sélections différentes ne partagent pas le cache ; ordre différent équivalent ; `200/206/400/403` correctement interprétés.
  - Commande : tests Vitest ciblés du service et du composable.
  - Sécurité : réutiliser `authFetch` exclusivement ; aucun repli vers les tables Supabase.
  - Retour arrière : revenir au constructeur d’URL actuel, les appels sans filtre restent valides.

- [x] **Créer l’état de filtres synchronisé avec l’URL.**
  - Fichiers : nouveau `src/composables/useAdminDashboardFilters.js`, `src/views/admin/DashboardView.vue`, tests unitaires.
  - Limites : initialisation depuis `route.query`, mise à jour avec `router.replace`, nettoyage des valeurs invalides, retrait unitaire, reset, un seul rechargement après une modification groupée.
  - Tests : restauration/rechargement, précédent/suivant, query invalide, reset et protection contre les réponses obsolètes.
  - Commande : tests Vitest ciblés.
  - Sécurité : l’URL ne contient que des identifiants de référentiel non sensibles ; le serveur revalide toujours.
  - Retour arrière : retirer le composable et conserver la période actuelle seule.

- [x] **Construire le panneau de filtres accessible et responsive.**
  - Fichiers : nouveau `src/components/admin/widgets/AdminDashboardFilters.vue`, `DashboardView.vue`, styles/tokens existants et tests composant.
  - Limites : barre résumée, compteur, filtres actifs supprimables, panneau progressif ; pas de refonte des cartes KPI ni du dashboard complet.
  - Tests : clavier, Échap, focus initial/restauré, noms accessibles, états chargement/erreur/vide, 320 px, tablette, desktop et zoom 200 %.
  - Commande : tests composants puis vérification visuelle locale.
  - Sécurité : les contrôles désactivés ne remplacent pas la validation serveur.
  - Retour arrière : retirer uniquement le composant, sans affecter le chargement non filtré.

- [x] **Valider la chaîne complète avant PR.**
  - Fichiers : tests existants du dashboard, tests de routes et documentation.
  - Limites : aucune modification de schéma ou de métrique hors filtre ; pas de déploiement automatique.
  - Tests : backend dashboard, sécurité, frontend service/composables/UI, build, navigation manuelle desktop/tablette/mobile.
  - Commande : commandes de validation du dépôt relevées dans `package.json`, puis build de production.
  - Sécurité : vérifier qu’aucune donnée personnelle ni clé Supabase n’apparaît dans les réponses, URLs ou logs.
  - Retour arrière : revert unique de la branche ; aucune migration à annuler.

## Critères de validation

- Les options visibles sont réelles, autorisées et chargées depuis le backend.
- Tous les filtres sont appliqués côté serveur ; une modification locale de l’URL ne contourne aucun droit.
- Les périodes courante et précédente utilisent exactement les mêmes filtres.
- Une combinaison sans sens est empêchée ou expliquée, puis refusée par l’API si elle est forcée.
- Les filtres actifs sont supprimables et « Réinitialiser » retrouve l’état sans filtre.
- L’URL permet de restaurer et partager la sélection sans exposer de donnée personnelle.
- Le cache ne mélange jamais deux sélections différentes.
- Le panneau est utilisable au clavier, à 320 px, sur tablette, desktop et à 200 % de zoom.
- Les appels existants sans filtre et les 16 KPI continuent de fonctionner.

## Risques et garde-fous

- Les métriques n’acceptent pas toutes les mêmes dimensions : la matrice d’applicabilité est contractuelle et testée.
- Les référentiels historiques peuvent contenir plusieurs graphies : les valeurs sont normalisées côté serveur et les valeurs inconnues ne sont pas acceptées silencieusement.
- Les filtres multiples peuvent augmenter le coût : limiter le nombre de valeurs et conserver le cache/dédoublonnage existant.
- Les changements Supabase récents sur l’exposition Data API n’imposent aucune action ici, car aucune nouvelle table exposée n’est créée.
- Si une vue/RPC devient nécessaire en cours d’implémentation, arrêter ce ticket et préparer une migration sécurisée séparée au lieu d’improviser un accès public.
