# Recherche — HEDS25-505

## Ticket

Le ticket Jira [HEDS25-505](https://hedsdev2025.atlassian.net/browse/HEDS25-505) demande un rapprochement fiable entre offres et propositions, restitué par institution, sans doubles comptes et avec signalement des données non rapprochées.

Le ticket ne contient aucune pièce jointe ni règle métier supplémentaire. Les deux décisions explicitement attendues concernent la période/PFP et le traitement des institutions possédant plusieurs sites ou variantes de nom.

## Modèle de données vérifié

Les deux valeurs à comparer sont stockées sur une même ligne de `places` :

- offres : champs JSON par type, `PFP1A`, `PFP1B`, `PFP2`, `PFP3`, `PFP4` ;
- propositions : champs JSON `pfp1a_proposition`, `pfp1b_proposition`, `pfp2_proposition`, `pfp3_proposition`, `pfp4_proposition` ;
- rattachement : `places.InstitutionId` pointe logiquement vers `institutions.InstitutionId` ;
- libellé de place : `places.NomPlace` ;
- libellé d’institution : `institutions.Name`.

Les objets annuels utilisent au moins deux formats de clé : année de fin (`2026`) et année académique (`2025-2026`). `TableauRecapitulatifOffres.vue` contient déjà `getAcademicYearKeys()` pour accepter les deux.

Le dépôt ne contient pas de migration créant la table `places` avec une contrainte étrangère vers `institutions`. La relation est donc traitée comme une convention applicative et doit être validée explicitement.

## Parcours actuel

### Chargement et jointure

`src/stores/placesStore.js` charge toutes les lignes `places` et `institutions` directement depuis Supabase, construit une map par `InstitutionId`, puis enrichit chaque place avec `Institution_name`.

Si une place référence un identifiant absent du référentiel, le store écrit seulement un avertissement console et utilise `place.Institution` ou `N/A`. Cette anomalie n’est ni exposée dans l’interface, ni exportée.

### Récapitulatif offres/propositions

`src/views/admin/formation-pratique/secretariat/TableauRecapitulatifOffres.vue` :

- compare offre et proposition par **place** et par type de PFP ;
- calcule les totaux globaux en additionnant toutes les places ;
- compte les institutions distinctes avec `Institution_name`, donc avec un libellé mutable plutôt qu’avec `InstitutionId` ;
- recherche et trie également sur le nom enrichi ;
- exporte une ligne par place ;
- ne produit aucune liste structurée des identifiants non rapprochés ou des doublons.

### Suivi par institution

`src/views/admin/formation-pratique/secretariat/SuiviOffresInstitutions.vue` regroupe correctement les places par `InstitutionId`, mais son indicateur « reçu » regarde uniquement les champs d’offre `PFP*`. Il ne rapproche pas les champs `*_proposition` et ne signale pas les places orphelines, car la vue part du référentiel `institutions`.

### Table de suivi inutilisée

`supabase/migrations/20260624_create_institution_offer_tracking.sql` crée `institution_offer_tracking` avec une unicité `(institution_id, year)`. Aucun des composants inspectés ne l’utilise. La table ne distingue ni le type PFP ni un éventuel site ; elle ne peut donc pas devenir la source du calcul sans décision métier et migration séparée.

## Autorisation et sécurité

- Les routes des deux vues déclarent `requiresAuth: true` et `need: 'page1.access'` dans `src/router/routes/pfp.js`.
- Les lectures sont néanmoins effectuées directement depuis le navigateur via Supabase ; la sécurité réelle dépend donc aussi des politiques RLS.
- La migration P0 `supabase/migrations/20260804211945_complete_p0_security_matrix.sql` couvre `institutions`, `places` et `institution_offer_tracking`. Toute nouvelle lecture serveur doit conserver la permission PFP existante et ne pas exposer les données à une route publique.
- Aucun besoin de nouvelle table, de secret ou d’accès anonyme n’est démontré pour ce ticket.

## Tests et conventions

Il n’existe aucun test ciblant `TableauRecapitulatifOffres.vue`, `SuiviOffresInstitutions.vue`, `getAcademicYearKeys()`, le regroupement par institution ou les lignes orphelines.

Les tests du dépôt utilisent Vitest pour les services et fonctions pures. La logique de rapprochement doit donc être extraite dans un module sans dépendance Vue/Supabase, puis testée avec des jeux couvrant :

- plusieurs places pour une institution ;
- noms différents pour un même `InstitutionId` ;
- mêmes noms pour deux identifiants distincts ;
- doublons de `PlaceId` ;
- identifiant d’institution vide ou inconnu ;
- valeurs nulles, vides, négatives ou non numériques ;
- clés annuelles `2026` et `2025-2026` ;
- chaque type PFP.

## Risques confirmés

1. **Comptage par nom** — deux variantes de nom peuvent créer deux institutions artificielles ; deux institutions homonymes peuvent être fusionnées.
2. **Absence de restitution des anomalies** — les places orphelines sont seulement visibles dans la console.
3. **Mélange de niveaux** — le récapitulatif affiche par place alors que le besoin Jira demande une restitution par institution.
4. **Doublons** — aucune déduplication explicite par `PlaceId` n’existe avant les sommes.
5. **Valeurs invalides** — `parseIntSafe()` transforme silencieusement toute valeur invalide en zéro, sans la signaler.
6. **Période implicite** — la vue choisit une année, mais aucune règle commune ne garantit que tous les calculs et exports utilisent la même interprétation.

## Direction recommandée

Conserver `places` et `institutions` comme sources, sans migration de données pour ce ticket.

1. créer un service pur de rapprochement utilisant `InstitutionId` comme clé canonique ;
2. dédupliquer par `PlaceId` et conserver les conflits dans une collection d’anomalies ;
3. agréger les offres et propositions par institution, année et type PFP ;
4. considérer chaque `InstitutionId` comme une entité distincte et agréger ses différents sites/places ; le nom sert uniquement à l’affichage ;
5. signaler séparément les `InstitutionId` absents, inconnus, les identifiants de place dupliqués et les valeurs non numériques ;
6. utiliser ce même résultat dans le tableau, les statistiques et l’export afin d’éviter trois règles différentes ;
7. protéger la logique avec des tests unitaires et documenter la règle.

## Décisions proposées à valider

- **Période** : année sélectionnée dans l’écran, avec support des clés `YYYY` et `YYYY-1-YYYY` déjà présentes.
- **PFP** : les cinq types existants, filtrables individuellement ou affichables ensemble.
- **Sites** : toutes les places portant le même `InstitutionId` sont agrégées dans la même institution ; deux identifiants différents restent distincts même si leur nom est identique.
- **Proposition reçue** : une institution est « avec proposition » si au moins une proposition strictement positive existe pour l’année et le périmètre PFP sélectionnés.
- **Anomalies** : aucune donnée n’est corrigée automatiquement ; les lignes non rapprochées sont visibles et exportables pour correction.
