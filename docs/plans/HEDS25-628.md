# HEDS25-628 — Sécuriser les accès et les votes de la postulation enseignants SI

## Périmètre validé

Sécuriser le parcours de postulation Soins infirmiers sans modifier les données
de production. `EnseignantSoins` gère uniquement ses propres votes, `RMSoins`
consulte et traite uniquement les votes des modules dont il est responsable ou
coordinateur, et `admin` supervise l'ensemble.

## Plan ordonné

### 1. Fermer la route aux autres utilisateurs authentifiés

- [x] Retirer le besoin générique `authenticated` de la route de postulation.
- [x] Autoriser uniquement `admin`, `RMSoins` et `EnseignantSoins`.
- [x] Vérifier le refus d'un rôle sans permission SI.

### 2. Appliquer la matrice dans l'interface

- [x] Réserver l'action de voter à `EnseignantSoins`.
- [x] Utiliser exclusivement l'identité Supabase courante comme propriétaire du
  vote.
- [x] Ne pas afficher aux enseignants les comptes ou identités des autres votes.

### 3. Sécuriser `planning_slot_votes` dans Supabase

- [x] Ajouter des fonctions serveur dédiées aux rôles SI actifs.
- [x] Remplacer la lecture globale des comptes authentifiés par des politiques
  séparées pour SELECT, INSERT, UPDATE et DELETE.
- [x] Permettre au RM de lire et nettoyer uniquement les votes des créneaux de
  ses modules ; permettre à l'admin la supervision globale.
- [x] Révoquer tout accès `anon`.

### 4. Prouver les autorisations avant publication sur test

- [x] Tester enseignant propriétaire, autre enseignant, RM propriétaire, RM non
  propriétaire, admin, utilisateur authentifié non SI et anonyme.
- [x] Lancer les tests ciblés et le build via Portly.
- [x] Publier uniquement sur `test.hedsvs.ch` après réussite des contrôles ; ne
  jamais appliquer cette migration à la production dans ce ticket.

## Retour arrière

La branche reste isolée. Une migration compensatoire pourra restaurer les
politiques précédentes sur la base de test ; aucune donnée de vote n'est
supprimée par la migration de sécurisation.
