# Plan d’implémentation — Design tokens de l’application

## Tâches

- [x] Consolider le contrat global des tokens.
  - Objectif : étendre `src/assets/styles/tokens.scss` avec des tokens
    sémantiques `--app-*` pour couleurs, typographie, espacements, rayons,
    ombres, contrôles, largeurs et mouvement.
  - Fichiers attendus : `src/assets/styles/tokens.scss`,
    `src/assets/styles/platform-foundations.scss`.
  - Autorisé : aliaser les variables PrimeVue et conserver les alias historiques.
  - Autorisé en complément : adoucir les surfaces du thème light et régénérer
    mécaniquement son CSS à partir des sources SCSS.
  - Interdit : modifier le jaune `#F3C300`, créer une nouvelle marque, introduire
    une notation isolée ou une nouvelle dépendance.
  - Tests : contrat de présence et de nommage des tokens; lint SCSS via build.
  - Validation : thème dim et light, contraste du jaune avec son texte, focus,
    contrôles et réduction du mouvement.
  - Sécurité : aucune donnée, permission, route ou configuration secrète.
  - Rollback : rétablir les deux feuilles globales; les alias historiques évitent
    une migration atomique obligatoire.

- [x] Migrer les composants fondamentaux vers le contrat.
  - Objectif : remplacer les valeurs répétées par les tokens dans les en-têtes,
    états système, formulaires, barre de tableau et layouts partagés.
  - Fichiers attendus : `PageHeader.vue`, `EmptyState.vue`, `ErrorState.vue`,
    `LoadingState.vue`, les primitives de `components/common/forms/`,
    `DataTableToolbar.vue`, `AdminLayout.vue` et `SocialThreeColumnLayout.vue`.
  - Autorisé : ajustements visuels mineurs nécessaires à la cohérence et aux
    deux thèmes.
  - Interdit : modifier la logique métier, les props/événements publics ou
    migrer toutes les vues de la plateforme.
  - Tests : tests existants des formulaires/layouts plus tests statiques empêchant
    de nouvelles valeurs magiques dans les composants migrés.
  - Validation : ordinateur, tablette et mobile; états normal, hover, focus,
    disabled, chargement, vide, erreur et succès.
  - Sécurité : conserver les éléments natifs, rôles ARIA et gardes existantes.
  - Rollback : rétablir les styles locaux sans toucher aux templates métier.

- [x] Documenter et rendre le système vérifiable.
  - Objectif : créer une page Docusaurus présentant catégories, conventions,
    exemples d’usage, thèmes et règles anti-valeurs-magiques.
  - Fichiers attendus : `documentation/docs/components/design-tokens.md`,
    `tests/unit/designTokens.spec.js` et, si nécessaire, la navigation docs.
  - Interdit : documenter des tokens non livrés ou recopier des données sensibles.
  - Tests : test de contrat, build Docusaurus et build Vite.
  - Validation : chaque critère du ticket doit être traçable dans la page et le test.
  - Sécurité : aucun secret ou contenu utilisateur dans les exemples.
  - Rollback : supprimer la page et le test avec le contrat associé.

- [x] Valider et préparer la PR.
  - Objectif : contrôler le diff, les thèmes et les tailles supportées avant
    publication sur une PR dédiée vers `prod`.
  - Commandes : tests unitaires ciblés puis suite pertinente, lint ciblé,
    `npm run build`, `npm run docs:build`, `git diff --check`.
  - Validation manuelle : captures dim/light aux largeurs desktop (1440 px),
    tablette (768 px) et mobile (390 px) sur au moins une page sociale, une page
    admin et un formulaire; vérifier aussi le reflow à 320 px.
  - Risque : changement global de cascade; vérifier l’ordre d’import et les
    fallbacks avant commit.
  - Rollback : revert du commit du ticket; aucune migration de données.

## Couverture des critères d’acceptation

- Couleurs, typo, espaces, rayons, ombres, contrôles et largeurs : tâche 1.
- Absence de nouvelles valeurs magiques dans les composants migrés : tâches 2 et 3.
- Conventions communes pour thèmes et états interactifs : tâches 1 et 2.
- Page de documentation avec usage : tâche 3.
