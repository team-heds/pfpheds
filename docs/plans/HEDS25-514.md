# Plan d’implémentation — cycle de vie des jetons de réinitialisation

## Objectif

Faire de Supabase Auth l’unique autorité du parcours, limiter les liens à une heure, garantir qu’un écran de récupération ne s’ouvre qu’après validation d’une preuve de récupération et fermer cette autorisation après un changement réussi.

## Tâche 1 — Versionner l’expiration serveur

**Objectif**

Ajouter un override Docker appliquant `GOTRUE_MAILER_OTP_EXP=3600` au service `auth` et faire charger cet override par le script de déploiement.

**Fichiers**

- nouveau `backend/deployment/supabase-auth-security.override.yml`
- `deploy-hedsvs.ps1`
- nouveau `tests/unit/supabaseAuthDeployment.spec.js`

**Limites**

- ne modifier ni les clés, ni SMTP, ni le contenu des emails ;
- ne créer aucune table de jetons ;
- ne changer ni les sessions globales ni les réglages OAuth hors récupération.

**Tests et commandes**

- test statique vérifiant la valeur 3 600 et la présence de l’override dans la commande Compose ;
- `npm run test:unit -- --run tests/unit/supabaseAuthDeployment.spec.js` ;
- validation Compose sur le VPS avant toute recréation du conteneur.

**Sécurité**

L’expiration est imposée dans GoTrue, pas dans l’horloge du navigateur. Aucun secret n’est ajouté au dépôt.

**Retour arrière**

Retirer l’override de la commande Compose et recréer uniquement le service `auth` avec la configuration précédente.

## Tâche 2 — Encapsuler le parcours de récupération

**Objectif**

Créer un service testable qui distingue une preuve de récupération d’une session ordinaire, traite les retours Supabase de façon contrôlée et consomme l’autorisation après le premier changement réussi.

**Fichiers**

- nouveau `src/service/passwordRecoveryService.js`
- `src/supabase.js` (désactivation de l'échange URL automatique uniquement sur les routes de récupération)
- nouveau `tests/unit/passwordRecoveryService.spec.js`

**Limites**

- réutiliser le client Supabase existant ;
- ne jamais stocker ou journaliser le jeton, le code, le mot de passe ou leur hash ;
- ne pas reproduire la validation cryptographique côté navigateur ; GoTrue reste l’autorité serveur.

**Tests et commandes**

- lien/code valide accepté une seule fois ;
- lien expiré refusé avec état contrôlé ;
- lien déjà consommé refusé ;
- session ordinaire sans preuve refusée ;
- deuxième changement avec le même contexte bloqué ;
- déconnexion demandée après succès ;
- `npm run test:unit -- --run tests/unit/passwordRecoveryService.spec.js`.

**Sécurité**

La logique frontend ne déclare jamais un jeton valide seule : chaque preuve est échangée ou vérifiée par GoTrue. Une garde mémoire empêche la double soumission et la session de récupération est fermée après succès.

**Retour arrière**

Revenir au traitement intégré dans `ResetPassword.vue` sans toucher aux données d’authentification.

## Tâche 3 — Brancher l’écran au cycle sécurisé

**Objectif**

Faire utiliser le service par `ResetPassword.vue`, supprimer l’acceptation d’une session générique, nettoyer l’URL sensible et conserver les messages accessibles pour les états expiré, invalide, consommé et réussi.

**Fichiers**

- `src/views/pages/ResetPassword.vue`

**Limites**

- conserver le design, la validation de complexité et le fallback OTP existants ;
- ne pas modifier les autres écrans d’authentification ;
- ne pas afficher de différence permettant d’énumérer les comptes lors de la demande d’email.

**Tests et commandes**

- tests du service de la tâche 2 ;
- `npm run test:unit -- --run tests/unit/passwordResetValidation.spec.js tests/unit/passwordRecoveryService.spec.js tests/unit/supabaseAuthDeployment.spec.js` ;
- test manuel : lien valide, lien réutilisé, lien expiré, dernier email après deux demandes, double clic sur Enregistrer.

**Sécurité**

Les erreurs console seront limitées à une catégorie et un code non sensible ; aucun objet d’erreur complet susceptible de contenir une URL ou un jeton ne sera écrit.

**Retour arrière**

Restaurer le composant précédent ; l’override serveur reste indépendant et peut être retiré séparément.

**Retour arrière**

## Correspondance avec les critères d’acceptation

| Critère | Couverture |
| --- | --- |
| Un jeton valide permet une seule modification | Validation GoTrue + garde de consommation + fermeture de session |
| Un jeton expiré est refusé | Expiration serveur à 3 600 s + état contrôlé |
| Un jeton déjà consommé est refusé | Effacement natif du `recovery_token` + test de réutilisation |
| Une nouvelle demande invalide les anciens jetons | Remplacement natif du jeton, règle “seul le dernier email est valide” documentée |
| Mot de passe stocké de façon sécurisée | `updateUser()` vers GoTrue, hash bcrypt natif, aucun stockage applicatif |
| Événements auditables sans secret | Audit GoTrue natif vérifié, logs applicatifs expurgés |
