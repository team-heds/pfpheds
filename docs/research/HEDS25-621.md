# HEDS25-621 — Retirer Firebase du domaine gamification

## Objectif et limites

Le ticket doit garantir que la gamification active de `test.hedsvs.ch` utilise
Supabase comme unique source de vérité. Il ne doit pas retirer Firebase des
domaines PFP, social, médias ou planning qui possèdent encore leur propre dette
technique. La production et les données ne sont pas modifiées par ce ticket.

Les critères issus de la feuille de route sont :

1. supprimer ou isoler les anciens services Firebase de gamification hors du
   bundle actif ;
2. migrer ou retirer les widgets Firebase ;
3. obtenir zéro import Firebase depuis le domaine gamification actif ;
4. obtenir zéro requête réseau Firebase pendant les parcours gamification ;
5. ne plus afficher les erreurs générales de configuration Firebase sur les
   pages Supabase-only.

Référence métier : `docs/plans/GAMIFICATION-SUPABASE-ROADMAP.md`.

## Architecture active vérifiée

- `src/router/routes/profiles.js` expose le profil, les quêtes, les défis, les
  badges et le classement des maisons.
- `src/router/routes/admin.js` expose le dashboard et les consoles Supabase de
  quêtes, défis, badges, utilisateurs et maisons.
- `src/components/gamification/GamificationProfilePage.vue` et
  `src/components/user/library/CardNameProfile.vue` lisent
  `src/service/gamificationServiceSupabase.js`.
- `src/components/gamification/ChallengesPage.vue` lit
  `src/service/challengesService.js`.
- `src/components/gamification/AchievementsPage.vue` lit
  `src/service/badgesService.js`.
- `src/components/gamification/QuestsPage.vue` lit
  `src/service/userQuestsService.js`.
- `src/components/admin/AdminDashboardGamification.vue` passe par
  `src/service/adminDashboardStatsService.js`, donc par le backend Supabase.
- `src/components/admin/ChallengeManagement.vue` passe par
  `src/service/adminChallengesService.js` et les RPC de cycle de vie livrées
  dans HEDS25-620.

Ces parcours constituent le chemin à conserver.

## Firebase encore atteignable depuis la gamification

### Route d'administration historique active

`src/router/routes/admin.js` expose toujours `/admin/defis` vers
`src/views/admin/institutions/gamification/AdminDefisView.vue`. Cette vue
importe `src/service/defisService.js`, qui lit et écrit directement le chemin
Realtime Database `defis`. La route est donc une seconde console de défis,
incompatible avec le cycle de vie Supabase de HEDS25-620.

La route moderne `/admin/gamification/challenges` et le composant
`src/components/admin/ChallengeManagement.vue` couvrent déjà ce besoin avec
validation, aperçu, transitions auditées et archivage.

### Services historiques non référencés par les parcours modernes

La recherche des imports montre que les modules suivants sont des implémentations
Firebase isolées du parcours moderne :

- `src/service/gamificationService.js` ;
- `src/service/hesHousesService.js` ;
- `src/service/questsService.js` ;
- `src/service/defisService.js` ;
- `src/service/notificationService.js`, qui dépend en retour de
  `gamificationService.js`.

`gamificationService.js` lit notamment `Users`, `challenges`, `quests`,
`gamification/badges`, `gamification/houses` et `gamification/logs` dans
Realtime Database. `hesHousesService.js` peut aussi écrire XP, maison et streak
depuis le navigateur. Ces comportements contredisent le moteur transactionnel
Supabase livré dans HEDS25-477, HEDS25-616 et HEDS25-619.

### Widgets historiques non montés

Les trois widgets suivants importent uniquement le service Firebase historique
et ne sont référencés par aucun écran ou route inspecté :

- `src/components/gamification/widgets/UserGamificationWidget.vue` ;
- `src/components/gamification/widgets/GamificationStatsWidget.vue` ;
- `src/components/gamification/widgets/GamificationActivityWidget.vue`.

`UserGamificationWidget.vue` importe en plus `getAuth` depuis `firebase/auth` et
utilise l'UID Firebase comme cible. Le dashboard actif possède déjà son
équivalent Supabase dans `AdminDashboardGamification.vue`. Le profil actif
possède déjà ses cartes Supabase dans `CardNameProfile.vue` et
`GamificationProfilePage.vue`.

## Pourquoi les erreurs Firebase apparaissent encore partout

`src/App.vue` utilise `useAuthStore` sur chaque page. Or
`src/stores/authStore.js` importe statiquement `@/firebase` et
`firebase/auth`, même si `isFirebaseUser` retourne toujours `false` et que les
routes actives utilisent uniquement Supabase.

Le module `firebase.js` ainsi chargé à l'initialisation journalise une erreur et
un avertissement quand les sept variables `VITE_FIREBASE_*` sont absentes.
C'est la cause directe des messages « Variables manquantes » observés sur les
pages Supabase-only. Les actions `signUpFirebase`, `signInFirebase` et
`resetPasswordFirebase` ne sont appelées que par l'ancienne vue
`src/views/auth/LoginView.vue`, qui n'est plus routée : `/`, `/home` et
`/login` aboutissent à `LoginHome.vue` ou à sa redirection Supabase.

La compatibilité `isFirebaseUser === false` peut être conservée temporairement
pour les écrans hors périmètre qui lisent encore ce getter, sans importer le
SDK Firebase dans le socle d'authentification.

## Dépendances Firebase hors périmètre

`firebase`, `firebase-admin` et `firebase-tools` ne peuvent pas encore être
retirés de `package.json`. Des modules PFP, social, médias, planning et stockage
les importent toujours. HEDS25-621 doit uniquement empêcher leur chargement par
le socle Supabase et par les routes de gamification.

Les colonnes `firebase_id` présentes dans Supabase sont des identifiants de
liaison historiques. Elles ne constituent pas des appels Firebase et ne doivent
pas être supprimées dans ce ticket.

## Sécurité Supabase et compatibilité actuelle

- L'utilisateur fiable provient de `supabase.auth.getUser()` dans les chemins
  de récompense. La documentation Supabase confirme que cet appel valide
  l'utilisateur auprès du serveur Auth.
- Les tables exposées restent protégées par RLS et les mutations de récompense
  passent par des RPC serveur. HEDS25-621 n'a besoin d'aucune migration.
- Les changements récents de Supabase sur l'exposition des nouvelles tables ne
  s'appliquent pas : aucune table n'est créée.
- Le changement self-hosted Envoy/Kong doit être traité par l'exploitation du
  VPS, pas par ce ticket frontend.

Références vérifiées le 21 septembre 2026 : changelog Supabase des breaking
changes, documentation `auth.getUser`, RLS et sécurisation de la Data API.

## Tests et preuves attendus

1. Test statique : aucun import `firebase/*` ou `@/firebase` depuis les routes,
   composants et services actifs de gamification.
2. Test du store : l'import et l'initialisation de `authStore` ne chargent plus
   Firebase ; l'authentification et la récupération de mot de passe restent
   Supabase-only.
3. Test de routage : `/admin/defis` redirige vers la console Supabase moderne.
4. Tests unitaires gamification existants : parcours utilisateur, dashboard,
   cycle de vie des défis, badges et services Supabase.
5. Build Vite avec uniquement les variables Supabase de test.
6. Vérification navigateur sur `test.hedsvs.ch` : profil, quêtes, défis,
   badges, classement et consoles admin ; aucune requête Firebase et aucune
   erreur de configuration Firebase.

## Risques et décisions

- Supprimer le SDK Firebase globalement casserait des modules hors périmètre :
  interdit.
- Réintroduire un fallback Firebase dans la gamification recréerait une double
  source de vérité : interdit.
- Conserver `/admin/defis` en lecture/écriture laisserait une console concurrente :
  la route doit rediriger vers `/admin/gamification/challenges`.
- Les fichiers historiques non référencés peuvent être supprimés de manière
  récupérable par Git. Si une dépendance inattendue apparaît au build, ils
  devront être isolés hors du graphe actif plutôt que reconnectés.
- Le dépôt est actuellement sur `codex/HEDS25-619-badges-challenges` avec de
  nombreux changements non validés appartenant aux travaux précédents. Aucune
  modification applicative HEDS25-621 ne doit commencer avant validation du
  plan et choix d'une branche sûre préservant cet état.

## Conclusion

Le ticket est réalisable sans migration et sans toucher aux données. Le noyau
du changement est : rendre `authStore` strictement Supabase, rediriger l'ancienne
console de défis, retirer les widgets et services Firebase non utilisés, puis
prouver par tests statiques, build et navigateur que la gamification active ne
charge plus Firebase.
