# Recherche — HEDS25-514

## Ticket

**Appliquer l’expiration et l’usage unique des jetons de réinitialisation**

Le ticket demande une validation serveur du jeton, une durée de vie limitée, le refus des jetons expirés ou consommés, l’invalidation des anciens jetons après une nouvelle demande, le stockage sécurisé du mot de passe et une piste d’audit sans secret.

## Parcours actuel vérifié

1. `src/views/auth/LoginHome.vue` appelle `authStore.resetPasswordSupabase(email)` avec une garde contre la double soumission.
2. `src/stores/authStore.js` appelle `supabase.auth.resetPasswordForEmail()` et redirige vers `/reset-password`.
3. `src/supabase.js` configure Supabase Auth en PKCE avec persistance de session et détection automatique des callbacks.
4. `src/router.js` laisse passer `/reset-password` et `/new-password` avant les contrôles d’authentification afin de ne pas perturber le callback PKCE.
5. `src/views/pages/ResetPassword.vue` accepte un code PKCE, des jetons implicites ou un OTP de récupération, puis appelle `supabase.auth.updateUser({ password })`.
6. `src/utils/passwordResetValidation.js` impose au navigateur huit caractères, majuscule, minuscule, chiffre et caractère spécial.

## Garanties Supabase vérifiées

La plateforme utilise une instance Supabase auto-hébergée. Le conteneur de production exécute `supabase/gotrue:v2.144.0`.

Le code source correspondant confirme que :

- `internal/api/verify.go` refuse un jeton si `RecoverySentAt + OtpExp` est dépassé ;
- `internal/models/user.go` efface `recovery_token` dans `Recover()` après la vérification : le lien est à usage unique ;
- `internal/api/mail.go` remplace `recovery_token` et `recovery_sent_at` à chaque nouvel envoi réussi : seul le dernier jeton reste valide ;
- `internal/crypto/password.go` stocke le mot de passe avec bcrypt ;
- `internal/api/recover.go` et `internal/api/user.go` écrivent les événements sensibles dans le journal d’audit.

La documentation Supabase actuelle confirme également que les liens d’authentification sont à usage unique, recommande une expiration OTP de 3 600 secondes ou moins et documente les actions d’audit `user_recovery_requested` et `user_updated_password` :

- https://supabase.com/docs/guides/deployment/going-into-prod
- https://supabase.com/docs/guides/auth/passwords
- https://supabase.com/docs/guides/auth/audit-logs

Le changelog Supabase a été contrôlé le 2026-08-06. Aucun changement récent ne remet en cause ce parcours. L’instance auto-hébergée devra néanmoins être mise à niveau séparément : la version GoTrue déployée est ancienne par rapport aux versions actuelles.

## État réel de production

Inspection non destructive du VPS :

- `GOTRUE_SITE_URL=https://hedsvs.ch` est défini ;
- `GOTRUE_MAILER_OTP_EXP` n’est pas défini ;
- GoTrue v2.144.0 applique donc son défaut historique de **86 400 secondes (24 h)** ;
- `auth.audit_log_entries` existe ;
- des entrées `user_recovery_requested` et `user_updated_password` sont présentes.

Aucune donnée personnelle, aucun jeton et aucun secret n’ont été lus pour cette vérification ; seuls la présence de la table et les comptes agrégés par action ont été consultés.

## Écarts et risques confirmés

### 1. Expiration trop longue

Le délai actuel est 24 h, alors que la recommandation Supabase de production est 1 h ou moins. La configuration n’est par ailleurs pas versionnée dans ce dépôt.

### 2. Une session ordinaire ouvre le formulaire de récupération

`ResetPassword.vue` termine par `supabase.auth.getSession()` lorsqu’aucun jeton n’est présent. Toute session Supabase existante peut donc ouvrir directement `/reset-password` et afficher le formulaire, même sans preuve qu’elle provient d’une récupération.

### 3. Le contexte de récupération n’est pas consommé dans l’interface

Après `updateUser`, la page affiche un succès mais ne détruit pas explicitement la session de récupération. GoTrue révoque les autres sessions lors du changement de mot de passe mais conserve la session courante. Une nouvelle soumission API resterait donc possible avec cette session tant qu’elle n’est pas révoquée.

### 4. Course possible avec la détection automatique PKCE

Le client Supabase a `detectSessionInUrl: true`, puis le composant appelle aussi `exchangeCodeForSession()`. La bibliothèque peut échanger et retirer automatiquement le code avant le montage du composant. Le composant écoute des événements d’authentification, mais il traite aussi un événement générique `SIGNED_IN` comme une récupération, ce qui ne permet pas de distinguer proprement les deux cas.

### 5. Couverture de test incomplète

Il n’existe aucun test du cycle de vie du jeton ou de `ResetPassword.vue`. `tests/unit/passwordResetValidation.spec.js` est vert. `tests/unit/authStore.spec.js` échoue déjà sur `prod` parce que son mock Firebase n’exporte pas `isFirebaseEnabled` ; cet échec préexistant est hors du périmètre fonctionnel du ticket et doit être signalé séparément, pas masqué.

## Direction recommandée

Conserver Supabase Auth comme seule autorité de jeton et de mot de passe. Ajouter une table maison dupliquerait une fonction sensible déjà correctement implémentée dans GoTrue et augmenterait la surface d’attaque.

Le correctif doit :

1. versionner un override Docker fixant `GOTRUE_MAILER_OTP_EXP=3600` ;
2. intégrer cet override au déploiement existant ;
3. isoler le cycle de récupération dans un service frontend testable ;
4. n’autoriser le changement qu’après une preuve de récupération explicite ;
5. consommer localement l’autorisation et fermer la session après le premier changement réussi ;
6. conserver les erreurs contrôlées sans journaliser de code, jeton ou mot de passe ;
7. documenter la règle : dernier jeton valide, expiration 1 h, usage unique.
