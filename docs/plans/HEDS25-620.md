# HEDS25-620 — Administrer le cycle de vie des quêtes et défis

## Objectif

Permettre à un administrateur habilité de préparer, vérifier, planifier,
publier, terminer et archiver une quête ou un défi sans exposer une
configuration incomplète. Toute transition doit être serveur, auditée et sans
notification automatique pendant le pilote.

## Décisions validées

- Environnement `test.hedsvs.ch` et base `staging` uniquement.
- États canoniques : `draft`, `scheduled`, `active`, `completed`, `archived`.
- Les dates sont interprétées par PostgreSQL et affichées en `Europe/Zurich`.
- Une quête/Un défi terminé ou archivé ne progresse plus, mais son historique
  et les progressions existantes sont conservés.
- La publication est une RPC administrative atomique ; le navigateur ne met
  plus directement le statut ni les assignations.
- Aucune notification email ou push n'est envoyée dans ce lot.

## Plan d'implémentation

- [x] Ajouter les états contrôlés aux quêtes et défis, sans invalider les
  données existantes, ainsi qu'un journal privé append-only des transitions.
- [x] Ajouter une validation serveur refusant dates incohérentes, récompense
  négative, quête sans étape ou étape liée à une action inconnue.
- [x] Ajouter un aperçu administratif sans écriture donnant l'état courant,
  l'état calculé, l'audience éligible, les assignations et les non-démarrés.
- [x] Ajouter une transition administrative atomique avec matrice d'états,
  attribution uniquement lors de l'activation et audit avant/après.
- [x] Ajouter un rafraîchissement serveur idempotent pour activer les éléments
  planifiés et terminer ceux dont la date est passée.
- [x] Planifier ce rafraîchissement sur la base test avec `pg_cron`, sans appel
  réseau ni notification.
- [x] Remplacer les écritures directes de l'interface admin par les RPC
  d'aperçu et de transition ; afficher les cinq états et les erreurs utiles.
- [x] Ajouter les tests SQL/RLS et unitaires couvrant validation, audience,
  transitions, clôture, audit, droits et idempotence.
- [x] Sauvegarder puis appliquer uniquement sur `staging`, rejouer le pilote et
  vérifier les vues admin/étudiant dans le navigateur.
- [x] Documenter les preuves dans Jira après confirmation avant publication du
  commentaire et changement de statut.

## Critères d'acceptation

1. Seul un administrateur habilité peut changer un état.
2. Une configuration invalide ne peut devenir ni planifiée ni active.
3. L'aperçu ne crée aucune progression ni aucun événement XP.
4. L'activation assigne une quête éligible une seule fois.
5. La clôture empêche toute nouvelle progression sans supprimer l'historique.
6. Chaque transition conserve acteur, ancien état, nouvel état, horodatage et
   résultat de validation sans secret.
7. Un rafraîchissement répété ne produit ni transition ni audit en double.

## Retour arrière

La migration est append-only. En cas d'anomalie sur test, désactiver la tâche
cron, restaurer les anciennes fonctions dans une migration compensatoire et,
si nécessaire, restaurer la sauvegarde effectuée avant application.
